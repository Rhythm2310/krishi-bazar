## 1. Mission
A bilingual (Bangla default, English switchable) farmer-to-buyer marketplace for Bangladesh,
rebuilt competition-grade: farmers register and list harvests with fair-price advice, buyers order
as guests with atomically reserved stock, and every rule (money in integer paisa, freshness from
real shelf-life windows, a strict order state machine) is pure, tested domain code. Done means:
all tasks in `.jules/plan.md` merged, the final review clean, `bun run verify` green, and the app
deployed on Vercel (Bun runtime) with Neon Postgres free tier and Vercel Blob, passing Lighthouse
budgets Perf ≥90 / A11y ≥95 / Best-Practices ≥95 / SEO ≥95.

## 2. Operating contract
1. You are one agent in a sequential chain of isolated VMs. You cannot see or talk to the others. The repo is the only channel; only merged code exists for you.
2. Open `.jules/tasks/<TASK_ID>-*.md` and execute only that task. Do not start other tasks, do not "helpfully" fix unrelated things.
3. Work autonomously. Never ask the user a question and never wait for approval. When something is ambiguous, apply the decision defaults in section 6, record the choice in your report, and keep going.
4. Change only the paths your task owns (section 5). Everything else is read-only.
5. Work test-first at the seams your task lists (skill `tdd`), review your own diff on both axes (skill `code-review`), then finish with: green verify command, clean `slop_guard`, a report at `.jules/reports/<TASK_ID>.md`, one PR.

## 3. Stack and commands
Runtime: **Bun 1.4.3** for install/dev/test/build; production runs on Vercel Functions with the Bun
runtime (`bunVersion: 1.4.x`, beta — ADR-0001 keeps `src/` runtime-agnostic: web standards and
`node:crypto` only, so `nodejs24.x` is a one-line fallback). SvelteKit 3.0.1, Svelte 5.57.2,
Vite 8.3.4, TypeScript 6.0.3 strict, Drizzle ORM 0.45.4, Neon (prod) / PGlite (dev+tests),
Zod 4.6.5. Dependencies: every package and version is pinned in `.jules/deps.csv` (researched
stable, non-deprecated releases). Use exactly those versions.

| Purpose | Command |
|---|---|
| Install | `bun install --frozen-lockfile` |
| Single test file | `bun run test:unit -- src/lib/domain/money.test.ts` or `bunx playwright test e2e/browse.spec.ts` |
| **Verify (run before every commit and before the PR)** | `bun run verify` |
| Slop and ownership check (same as CI) | `python .jules/tools/swarm.py guard` |
| Local database | `bun run db:reset` then `bun run db:seed` (zero external services — ADR-0004) |

`bun run verify` runs svelte-check, eslint, prettier check, vitest (with coverage gates),
playwright and build exactly as CI does. During the loop run types and single test files often,
and the full suite once at the end. Do not add or change dependencies (5.5). Read secrets from
environment variables documented in `.env.example`; never hardcode them. Locally both env vars may
be unset: the app then runs on PGlite and local photo storage automatically.

## 4. Architecture map and language
```
src/
  routes/            SvelteKit pages + form actions: / (marketplace), /p/[id], /order/[id],
                     /farmer/{register,login,logout,listings,orders}, /api/{health,upload}
  lib/domain/        PURE rules, no I/O (seam S1): money (paisa), units, freshness,
                     order-machine, rate-limit, validate (zod), pricing, clock (Asia/Dhaka)
  lib/data/          Frozen researched data: taxonomy (~100 categories: windows, units, seasons,
                     piece weights, reference prices + provenance), districts (64), rates
  lib/db/            Drizzle schema (contract) + PGlite↔Neon adapter (ADR-0004)
  lib/server/        Server modules (seam S2): auth, upload, listings, market, orders, comments
  lib/i18n/          Typed dictionaries bn/en (per-module drop-in files), cookie store, Intl formatters
  lib/photos/        Client WebP conversion (pure helpers) + upload client
  lib/components/    ui primitives, layout, listings, market, orders, comments, pricing, photos, auth
  styles/            tokens.css (frozen design tokens), base.css — components consume tokens only
  hooks.server.ts    Security headers, locale cookie, session locals
drizzle/             SQL migrations (generated by drizzle-kit, single owner)
e2e/                 Playwright specs (seam S3), one file per feature + smoke
scripts/             db/ (migrate, reset, seed), lighthouse/ (budget checker)
```
Dependency direction (never reverse): `routes/components → lib/server → lib/db + lib/domain → lib/data`.
`lib/domain` imports nothing from db, server, routes or Svelte. UI text reaches the screen only
through `lib/i18n` dictionaries.

**Language.** `GLOSSARY.md` defines the domain words (Farmer, Buyer, Listing, Order, Stock, Unit,
Paisa, Fair price, Grade, Organic claim, Freshness, Delivery speed, Comment, Verified buyer,
Session, Locale, Category, Season, District, Expired order). Name code, tests, commits and PR text
after them (skill `domain-language`). Surprising decisions are in `docs/adr/` — read the ones in
your area; ADR-0002 (paisa money) binds every money path.
**Design.** Deep modules: much behaviour behind a small interface, placed at a seam (skill
`codebase-design`). The frozen contract is a module's interface.
Conventions:
- Money is `integer paisa` end to end; round half-up in `domain/money` only; display via i18n formatters (Bengali numerals in `bn`).
- Dates: all "today"/freshness/expiry logic through `domain/clock` (Asia/Dhaka); raw `new Date()` only inside it.
- Files kebab-case; identifiers camelCase; types PascalCase; test files `*.test.ts` beside source; e2e `e2e/<feature>.spec.ts`.
- Errors: form actions return `{ ok:false, fieldErrors }` keyed by zod issue paths, messages via dictionary keys; API routes return JSON `{ error, code }` with proper status.
- Forms use SvelteKit form actions with progressive enhancement (`use:enhance`); mutations never use client `fetch`.
- Styling: scoped component CSS + token variables only; no raw color hex values in components; dark theme = token swap.
- Every user-visible string lives in both `bn` and `en` dictionaries (parity test fails the build otherwise).

## 5. Collision protocol (non-negotiable)
Agents run sequentially, but ownership keeps the chain honest and the guards run on every PR.

5.1 **Owned paths are exclusive.** Your task file lists them under `owns`. You may create, edit and delete files there. Nowhere else.
5.2 **Hot files are never edited by you** unless your task owns them: `package.json`, `bun.lock`, tool configs (`tsconfig.json`, `svelte.config.js`, `vite.config.ts`, `playwright.config.ts`, `eslint.config.js`, `.prettierrc.json`, `.prettierignore`, `commitlint.config.js`), `vercel.json`, `.github/workflows/**`, `src/app.html`, `src/app.d.ts`. Need a change there? Follow 5.7. Shared surfaces that deepen across the sequential chain (`src/hooks.server.ts`, `src/routes/+page.svelte`, `vitest.config.ts`, `scripts/**`, `static/**`, `e2e/**`) are governed by each task's `owns` in `.jules/tasks.csv` — edit them only when your task file lists them.
5.3 **Contracts are frozen:** `src/lib/db/schema.ts`, `drizzle/**`, `src/lib/data/{taxonomy,districts,rates}.ts`, `src/lib/domain/{money,units,freshness,order-machine,rate-limit,validate,clock}.ts`, `src/lib/i18n/index.ts`, `src/lib/i18n/format.ts`, `src/styles/**`. Read them, never edit them, unless your task file owns them. If a contract looks wrong, follow 5.7.
5.4 **No drive-by edits.** No reformatting, renaming, moving, import reordering or dependency bumps outside your owned paths. Formatters run only on files you changed.
5.5 **No new dependencies and no version changes.** All dependencies are pre-installed at the pinned stable versions in `.jules/deps.csv` by T01. If one is missing, deprecated, vulnerable or broken, write a request (5.7) and use a local stub. Use the API of the pinned version, not of an older one you remember.
5.6 **Drop-in registries.** i18n dictionaries auto-merge from `src/lib/i18n/{bn,en}/*.ts` (import.meta.glob); routes are file-based; e2e specs are auto-discovered by the Playwright config. Add your own new file; leave shared index or barrel files alone.
5.7 **Requests instead of edits.** To ask for a change outside your paths, create `.jules/requests/<TASK_ID>-<slug>.md` stating the file, the exact change and why. Then continue with a stub or adapter inside your own paths. Never block on it.
5.8 **Git hygiene.** Branch `jules/<TASK_ID>-<slug>`. Commits `<type>(<scope>): <summary> [<TASK_ID>]` (conventional; commitlint runs in CI). PR title starts with `[<TASK_ID>]`. One PR per task. Never force-push, never merge, never touch `main` directly. `swarm.py status` infers merged tasks from `[T..]` PR titles and `jules/T..` branch names — keep both conventions.
5.9 **Generated files** (`drizzle/**`, `.svelte-kit/`, `build/`, coverage output) are regenerated by tools, never hand-edited.
5.10 **Reserved:** `AGENTS.md`, `GLOSSARY.md`, `docs/adr/**`, `.jules/spec.md`, `.jules/swarm.json`, `.jules/README.md`, `.jules/plan.md`, `.jules/tasks/**`, `.jules/tasks.csv`, `.jules/ownership.csv`, `.jules/skills.csv`, `.jules/deps.csv`, `.jules/tools/**`, `.agents/skills/**` belong to the architect. Read them; request changes (5.7).

## 6. Autonomy rules
Decision defaults (use without asking):
- Simplest design that satisfies the acceptance criteria; reuse `lib/components/ui` primitives before creating new ones.
- Validation: reuse the zod schemas in `src/lib/domain/validate.ts`; every form action re-validates server-side and returns field errors; never trust client state.
- Money: convert taka↔paisa only via `domain/money`; totals only via the pricing functions; never `parseFloat` on money.
- Stock changes only through `lib/server/orders` atomic reservation/release helpers.
- State changes only through `domain/order-machine` transitions; every write is one atomic SQL statement or transaction.
- Locale: `bn` is the default; new strings need both dictionaries in the same PR.
- Auth-gated pages: guard in the nearest `+layout.server.ts`; redirect to `/farmer/login?returnTo=<path>`.
- Empty and error states are part of every UI surface; use the ui primitives and dictionary strings.
- Test only at the seams in your task file (S1/S2/S3). If they cannot express a needed test, test through the public interface of a module you own and note it in the report.
- A glossary term is missing: use the closest glossary term and file a glossary request (skill `domain-language`).

When stuck:
1. Same failure three times: stop retrying that approach. Take the fallback in your task file, or the simplest alternative inside your owned paths.
2. A prerequisite from another task is missing: build a minimal stub behind the contract interface inside your paths, note it in your report, continue.
3. You cannot meet an acceptance criterion: finish everything else, put `[PARTIAL]` after the task ID in the PR title, and list the gap in the report. A partial PR beats no PR.

- [ ] Self-review done on both axes (Spec, then Standards); every hard finding fixed, every leftover listed with its reason.

## 8. CI Auto-Fixer rules
CI Auto-Fixer may push fixes to your PR when CI fails. Whenever you are fixing a failing check:
- Read the failing log first. Fix the root cause.
- Edit only files your task owns. The `ownership-guard` check fails the PR otherwise.
- Keep every test and rule intact: no skipping, deleting, weakening or `xfail`; no loosened lint or type rules, coverage thresholds or Lighthouse budgets; no edits to `.github/workflows/**`; no snapshot update without reading the diff and confirming the new behaviour is intended; no `slop-ok:` marks added to satisfy `slop_guard`.
- If the failure comes from code you do not own, add a PR comment naming the file and failing check, file a request (5.7), make your own code robust if possible, and stop.
- After three fix attempts on one failure, stop and summarize in the PR.
